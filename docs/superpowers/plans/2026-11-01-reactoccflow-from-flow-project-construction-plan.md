# ReactOccFlow：从流程方案到可运行项目的建设规划

> 编写日期：2026-11-01。
> 起点假设：已有整理好的研究流程，但暂不把现有代码、缓存和实验视为已完成交付，按从零建设来安排任务。实际执行时，已有成果通过对应验收即可复用，无需推倒重建。
> 本文是[权威实施计划](2026-10-27-reactoccflow-implementation-plan.md)的入门执行分解，遵循其中最新的标准 DiT 路线；不替代原计划、实施进展或训练暂停记录。本次交付为规划文档，没有执行环境安装、代码迁移或训练。

## 1. 建设目标与顺序

最终系统接收当前及历史观测，生成自车候选轨迹，预测各候选下的未来 occupancy 与 actor 运动，估计并校准风险，再选择轨迹交给控制器。

按单人开发、两张 GPU、12–16 周的原计划安排。以下周数是工作量估计，不是实验效果承诺；数据准备、仿真安装或模型收敛超出预期时，以阶段验收决定后续进度。

| 阶段 | 时间估计 | 主要工作 | 可检查的交付 | 对应原计划 |
| --- | --- | --- | --- | --- |
| P0 项目构建 | 第 1 周 | 专用环境、独立包、配置、命令入口、来源保护、构建隔离 | 安装 wheel 后可在项目外运行环境检查，参考仓库前后无变化 | T0–T1 |
| P1 编解码与最小模型链路 | 第 2–3 周 | 迁移单套 VAE 及必要基础层；建立标准 DiT 的最小前向、FM 目标与采样 | 自有权重可加载；occupancy 编解码与合成输入采样形状正确 | T2–T3 的迁移基础；遵循后续 DiT 决策 |
| P2 真实研究数据 | 第 3–4 周 | scene/token 索引、E0 坐标、actor 标签、数据划分、独立 latent 缓存 | 至少 20 个场景可视检查；时间、坐标、mask 和防泄漏检查通过 | T4–T5 |
| P3 联合世界模型 | 第 5–6 周 | occupancy-only、parallel、joint 三种对照；双向交互与一致性损失 | 200 步短跑、32 窗口拟合、单卡/双卡恢复通过，再进入正式训练 | T6–T7 |
| P4 反应式数据与验证 | 第 6–8 周 | 同初始场景下实际执行不同 ego 动作，记录 NPC 响应 | 小规模分支数据和响应报告；验证通过后扩大采集 | T8–T9 |
| P5 候选规划与风险校准 | 第 8–10 周 | PlanFlow、显式刹停候选、多世界风险、独立校准与轨迹选择 | 单场景可输出候选、风险、最终轨迹及选择原因 | T10–T11 |
| P6 真实点云前端 | 第 9–11 周 | LiDAR→occupancy latent；当前 actor 检测与历史关联 | 关闭 oracle 输入后仍可生成计划，并单独报告感知质量 | T12–T13 |
| P7 仿真闭环 | 第 11–13 周 | 消息协议、控制跟踪、超时处理与 CARLA/Bench2Drive 评测 | 完成传感器输入到控制输出的闭环，保存成功与失败记录 | T14–T15 |
| P8 实验与复现交付 | 第 13–16 周 | 多种子、结构/采样消融、效率测量、实验表与复现包 | 指标可由保存的预测重算，主要实验可按文档复现 | T16–T17 |

阶段可以部分重叠，但结果有依赖：P2 数据验收先于 P3 全量训练；P4 的真实动作执行标签先于 P5 的反应式风险校准；P6 前端接入先于完整传感器闭环结论。第一周可只读盘点仿真依赖和磁盘预算，提前暴露后续条件缺口。

**第一个值得完成的目标是 P0：把流程方案变成一个可以安装、检查和独立运行的工程。** 本阶段的合成张量只验证工程行为，不作为预测效果或规划效果。

## 2. 项目构建前固定的设计约定

| 项目 | 首版约定 | 固定它的目的 |
| --- | --- | --- |
| 项目包 | `reactoccflow` | 代码统一从自有包导入 |
| 环境 | `/home/lthpc/wxh/envs/ReactOccFlow` | 与参考工程环境分开维护 |
| 世界模型主干 | 标准 DiT；patch=5、hidden=256、depth=8、heads=8 | 按最新路线建设，不重新加入旧 U-Net 运行分支 |
| occupancy 表示 | 单套 VAE；latent 为 `16×50×50` | 历史和未来标签分别编码，不额外引入第二套 VAE |
| 坐标 | 当前自车 E0；x 向前、y 向左、z 向上；米、秒 | 数据、几何、预测和风险使用相同定义 |
| occupancy 网格 | `200×200×16`，0.4m；范围 `[-40,40]×[-40,40]×[-1,5.4]` | 避免网格与权重、标签不兼容 |
| 时间 | 6 个历史 latent 槽，默认最近 4 槽有效；未来 6 个时刻，标称 0.5–3 秒 | 缺帧通过 mask 表达；标签保存实际时间间隔 |
| actor | 按当前可见距离与稳定 token 选最近 8 个，历史 4 帧 | 防止用未来出现、运动或碰撞情况挑选目标 |
| 首版研究输入 | oracle occupancy/actor 表示；后续独立接入 LiDAR | 各阶段分别验收表示建模和实际感知能力 |
| 随机性 | 数据划分、训练噪声、推理采样分别管理随机数状态 | 便于复现与断点恢复 |

核心推理链路：

```text
当前与历史观测 → 场景表示 → 自车候选轨迹
                            ↓
                  候选条件的联合未来生成
                            ↓
              多世界风险 → 校准 → 轨迹选择 → 控制
```

训练标签走单独的数据通路。候选轨迹是系统计划执行的控制条件，可以输入世界模型；未来专家轨迹、未来 occupancy 和未来 actor 真值属于监督信息。

## 3. 第一阶段目录与模块职责

采用当前工程的 `training/` 命名承接原计划的训练引擎职责，避免同时建立两套 `engine/` 与 `training/`。

```text
Paper/
├── AGENTS.md
├── README.md
├── pyproject.toml
├── requirements-lock.txt
├── THIRD_PARTY_NOTICES.md
├── reactoccflow/
│   ├── __init__.py           # 版本与包入口
│   ├── __main__.py           # python -m reactoccflow 命令入口
│   ├── provenance.py         # 普通文件复制、校验与参考保护
│   ├── data/                 # 样本契约、索引、标签和缓存
│   ├── geometry/             # 坐标、网格与车体几何
│   ├── models/               # VAE、标准 DiT 与联合 FM
│   ├── losses/               # 联合一致性约束
│   ├── training/             # 优化、验证、DDP 和恢复
│   ├── planning/             # 候选生成与轨迹选择
│   ├── evaluation/           # 预测、响应、风险与校准评价
│   ├── perception/           # 后续真实点云前端
│   └── simulation/           # 后续分支采集、通信与控制
├── configs/                  # 独立配置，不继承参考仓库
├── scripts/                  # 自有的数据准备、训练和审计入口
├── tests/                    # 按职责组织的测试
├── data/                     # 自有索引、复制缓存和生成数据
├── assets/checkpoints/       # 按需复制的自有权重
├── outputs/                  # 日志、预测、图件与实验记录
├── docs/
│   ├── superpowers/plans/    # 实施与阶段规划
│   ├── provenance/           # 检索、来源、校验值和参考快照
│   └── implementation/       # 已执行的检查与验收证据
├── OccFM/                    # 只读参考，不参与构建与运行
└── IR-WM/                    # 只读参考，不参与构建与运行
```

P0 先实现包入口、配置、来源保护与基础检查，其余目录明确职责即可。模型和业务模块按阶段实现；未实现的功能不得返回伪造预测或被标为可用。表中的文件是目标交付，已有同名文件需要按验收条件核对后复用。

## 4. 第一周逐日执行任务

### 第 1 天：明确边界并保存参考基线

**输入**：流程方案、权威计划、两个本地参考仓库。

1. 写明首版输入、输出、标准 DiT 路线，以及 oracle、实际感知、闭环各自的交付边界。
2. 保留并核对根目录 `AGENTS.md`，固定参考目录只读、先检索后迁移、未来标签隔离和专用环境规则。
3. 以只读方式记录两个参考仓库的 HEAD、完整 Git 状态、已有未跟踪文件及内容快照。Git 查询关闭可选写锁；遍历不跟随目录链接，不执行参考脚本。
4. 对源码、配置和许可证计算 SHA-256；记录其他文件的清单、类型、大小等元数据。待迁移的权重和缓存另外做完整内容校验。
5. 盘点 GPU、驱动、磁盘、独立数据目录和仿真依赖，只读记录可用条件与缺口。

**交付**：`docs/provenance/reference_snapshot.json`、`docs/provenance/search_log.md`、`THIRD_PARTY_NOTICES.md`、构建范围说明。

**验收**：能够解释参考仓库的所有既有改动；后续比较使用本次起点快照，保留原有历史快照。不能通过 reset、clean、删除或改名参考目录来获得“干净状态”。

### 第 2 天：准备专用环境并建立可安装包

1. 检查专用环境；已存在时先核对与复用，不覆盖或重建现有环境。
2. 根据原计划已验证的组合准备 Python 3.10、PyTorch 2.7.1 对应 cu128 构建、NumPy 1.26.4。安装前核对本机驱动兼容性；这些版本来自既有计划，本轮未重新验证环境。
3. 在 `pyproject.toml` 声明构建后端、项目依赖和开发依赖，仅发现并打包 `reactoccflow*`。
4. 建立版本入口和 `doctor` 命令。检查 CPU 张量运算、CUDA 可用性，以及每张 GPU 的独立基础运算。
5. 锁定实际验证过的第三方依赖，另存项目 wheel 的版本和 SHA-256；不把当前机器的本地 wheel 绝对路径当成可移植安装依赖。

**交付**：`pyproject.toml`、`requirements-lock.txt`、`reactoccflow/__init__.py`、`reactoccflow/__main__.py`、`docs/implementation/environment.json`。

**验收**：专用环境可构建、安装和导入包；CPU 与两张 GPU 分别通过基础检查。双卡 DDP 的通信及训练恢复另在 P3 验收。核心训练依赖不引入参考工程的旧 OpenMMLab 或 Lightning 环境。

### 第 3 天：建立自有配置与运行记录

1. 将数据根目录、输出目录、设备、随机种子和坐标/网格版本集中配置。
2. 原始数据指向独立目录 `/home/lthpc/data/nuscenes`，仅做读取；生成数据、日志和检查点写入项目自有目录。
3. 配置加载后检查路径、类型和数值范围，拒绝指向参考目录的运行资源路径。
4. 对每次运行保存解析后的配置、环境版本、源码身份、种子、开始/结束状态及失败原因。输出目录存在时显式选择恢复或新实验，不静默覆盖。
5. 更新 `.gitignore`，排除数据、权重、构建产物、字节码和训练输出。

**交付**：独立配置与加载约定、运行记录格式、日志及输出管理、README 的安装与环境检查说明。

**验收**：同一入口在不同工作目录下按明确路径规则解析配置；错误路径和错误参数提前报错；日志能定位对应配置与源码。

### 第 4 天：固定数据契约与监督边界

1. 定义 `observation`、`target` 和 `metadata`，明确每个字段的来源、坐标、单位、dtype、shape 和 mask。
2. `observation` 仅含当前与历史信息；未来标签及未来真值有效性 mask 放入 `target`；scene/token、版本和来源放入 `metadata`。
3. 候选计划独立作为世界模型的控制条件；训练中使用的日志真实 ego 轨迹只表示已执行动作，不当成可任意替换的反事实标签。
4. 用小型合成样本检查字段、shape、空 actor、历史缺失及 mask，检查推理边界拒绝未来真值。
5. 记录数据拆分方案：nuScenes 官方训练场景固定划分为 train/tune/calibration，官方 val 保留最终评价。归一化只在 train 拟合。

核心字段约定：

| 所属 | 字段 | 主实验形状 | 使用边界 |
| --- | --- | --- | --- |
| observation | `history_latents` | `[B,6,16,50,50]` | 仅历史 |
| observation | `history_mask` | `[B,6]` | 历史有效性 |
| observation | `ego_state` | `[B,4]` | 当前状态 |
| observation | `actor_history` | `[B,8,4,6]` | 当前与历史状态 |
| observation | `actor_observed_mask` | `[B,8,4]` | 观测可用性 |
| observation | actor 类别、尺寸等 | 按接口明确 | 来自当前观测 |
| control | `ego_candidate_xy` | `[B,K,6,2]` | 系统生成的候选计划；逐候选调用可取 `[B,6,2]` |
| target | `future_latents` | `[B,6,16,50,50]` | 训练与离线评价 |
| target | `actor_future` | `[B,8,6,6]` | 训练与离线评价 |
| target | `actor_target_mask` | `[B,8,6]` | 损失与评价，不能输入推理 |

**交付**：数据契约文档、字段验证、合成样本和边界测试。真实标签提取、完整缓存生成属于 P2。

**验收**：输入与监督字段可以明确分离；actor 选择规则不读取未来。P0 先验收接口拒绝行为；P3 再验证固定观测与种子时，删除或打乱未来 target 不改变模型推理结果。

### 第 5 天：建立“检索—复制—改造—审计”工作流

每一个待实现函数都先搜索两个参考仓库，包括基础工具和没有直接模型计算的功能。

1. 在 OccFM 和 IR-WM 中只读搜索相应功能、相关类和依赖。
2. 找到适用实现时，列出必要代码、配置、基础层、资源及外部依赖，形成依赖闭包。
3. 将必需部分复制为项目自有普通文件，再修改包内导入和资源解析。
4. 记录来源 commit、源路径、源文件 SHA-256、目标路径、目标校验值、源文件已有改动、许可证和适配说明。
5. 两个参考仓库都没有适用实现时，记录搜索词、搜索范围、结果与新增理由，再在独立包内实现。
6. 保留原版权/许可证头。OccFM 的未明确许可状态写入 `THIRD_PARTY_NOTICES.md`，不能据此假定拥有公开发布派生代码的授权。

**交付**：来源记录格式、迁移/校验工具、首批基础功能的来源清单；不提前复制无关模型、缓存或全部权重。

**验收**：无软链接、硬链接、参考目录导入、editable 安装参考项目、`sys.path`/`PYTHONPATH` 注入、`.pth` 路径依赖或参考配置继承。参考目录路径仅可作为来源文档信息保留。

### 第 6–7 天：构建、隔离检查并交付 P0

1. 运行包入口、配置、数据契约、普通文件迁移和参考保护的基础测试。
2. 构建 wheel，检查压缩包内容和安装元数据，确认不包含参考仓库或指向参考仓库的运行依赖。
3. 安装普通 wheel，在项目外的临时目录以 `python -I` 运行导入和 `doctor --cpu-only`；核对模块实际从专用环境的安装目录加载。
4. 审计链接、运行资源路径和导入位置。隔离进程应拒绝访问参考目录；用受控文件访问限制验证，不能仅凭“临时目录下没有同名目录”证明隔离。
5. 对照第 1 天快照检查两个参考仓库，确认内容、Git HEAD、既有改动和生成文件均未改变。
6. 保存 P0 验收报告，逐项标记通过、失败、未执行与证据路径；README 写出下一阶段入口。

**交付**：wheel、环境报告、参考保护报告、基础隔离报告、安装/检查文档和 P0 验收清单。

**验收**：下节所有 P0 检查项通过。P0 只验收基础包；VAE 资源和 DiT 接入后，在 P1 扩展到编解码与采样隔离检查；P3 再扩展到独立训练、恢复和评价。

## 6. 第一阶段命令约定

下面是后续执行时的命令示例，本次未运行。环境已存在时先核对；仅在尚不存在时创建：

```bash
conda create --prefix /home/lthpc/wxh/envs/ReactOccFlow python=3.10
conda activate /home/lthpc/wxh/envs/ReactOccFlow
```

确认驱动兼容并安装声明的第三方依赖后，在项目根目录构建和安装普通 wheel。开发工具包含 `build` 与 `pytest`：

```bash
python -m build --wheel
python -m pip install --no-deps --force-reinstall dist/reactoccflow-0.1.0-py3-none-any.whl
python -m reactoccflow doctor --output docs/implementation/environment.json
python -m pytest -q
```

## 7. P0 之后的具体推进方式

### P1：先验证表示和最小计算链路

- 搜索并迁移 VAE 依赖闭包与权重，核对缺失/多余参数；只保留一套 encoder/decoder。
- 先检查单帧 occupancy→latent→重建；固定输入保存数值、shape 和可视化证据。
- 建立标准 DiT 的 patch 投影、时空 token、条件编码、速度输出及 unpatchify，使用合成输入检查 FM 目标和积分器。
- 固定历史条件，仅积分未来；同种子采样可复现。旧兼容缓存可用于表示兼容性检查，研究指标使用 P2 的统一 E0 数据。
- 从独立普通文件加载资源，完成安装包的编解码/采样隔离验收。此时仍不宣称模型具有预测质量。

### P2：先把真实数据做对

- 从官方表建立 scene/sample/instance 索引，禁止跨 scene 拼接窗口。
- 将历史及未来监督 occupancy 先在三维空间转换到 E0，再编码；不能将二维 latent warp 当作精确三维变换。
- 按当前观测选择 actor，处理无目标、消失、缺帧、未知区域和场景尾部。
- 固定 560/70/70/150 场景的 train/tune/calibration/evaluation 划分，归一化只从 train 拟合。
- 先生成和人工检查至少 20 个场景，再分片生成全量缓存，保存时间、网格、坐标、来源和内容校验值。
- 核对复用权重的预训练暴露：已有 VAE 若见过官方 700 个训练场景，新划出的 tune/calibration 不能称为整个管线严格未见。严格独立的校准结论需解决这一暴露问题。

### P3：按对照逐步增加联合建模

- 先运行标准 DiT occupancy-only，再运行 occupancy/actor parallel，最后运行 joint。
- 在第 4 个 DiT Block 后接 actor self-attention 和同步双向 cross-attention，两种模态分别输出速度，共享生成流时间。
- 先验证 FM 损失和有效梯度，再依次加入 occupancy–actor、静态时序和类别运动学约束；冻结 VAE 参数时保留 decoder 对预测 latent 的输入梯度。
- 完成 200 步短跑、32 窗口小样本拟合及恢复验收，记录明确通过标准后才扩大训练。小样本 loss 降低不替代真实预测评价。
- 使用一致的数据与采样预算比较 occupancy mIoU、动态类 IoU、actor ADE/FDE 及概率预测指标，保留每种配置的原始预测和日志。

### P4–P5：有真实执行标签后验证响应与校准

- 先做 10 类场景、每类 10 个初始状态的分支验证；同初始状态下实际执行不同候选动作，允许 NPC 响应，并保存实际轨迹、事件及跟踪误差。
- 按初始场景分组划分数据，同一 origin 的所有动作和种子进入同一划分；小规模验证通过后再扩展到原计划约 24,000 次分支 rollout。
- PlanFlow 的日志训练阶段只使用实际执行的 ego 轨迹监督；任意扰动候选不能沿用日志未来作为反事实真值。
- 默认生成 8 条候选，另加一条显式刹停候选；每候选采样 8 个世界、8 步积分，记录完整计算预算。
- 用实际执行对应候选后的事件拟合校准器，阈值在 tune 确定后冻结；报告 Brier、NLL、ECE、可靠性图及事件数量。无反事实标签时只能交付接口与离线几何诊断。

### P6–P8：把表示实验接成传感器闭环并完成交付

- 训练 LiDAR occupancy/latent 前端与当前 actor 检测、关联，分别报告 oracle 和真实感知结果。
- 模型与 CARLA 分进程，通信携带版本、episode、时间戳和序号，拒绝未来真值与过期计划。
- 先用简单路线验证消息、轨迹跟踪、超时和刹停，再扩大路线与随机种子，保留崩溃和失败样本。
- 目标为规划 2Hz、控制 20Hz；实测感知、候选、世界采样、解码、风险和通信耗时后报告是否达到目标。
- 完成多种子和消融，保存可重算指标的预测、校准器、配置及权重，复现包包含声明的数据和独立运行说明。
